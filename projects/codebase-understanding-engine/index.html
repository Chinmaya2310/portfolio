Codebase Understanding Engine

Joining a new codebase usually means days of opening files one by one. CUE makes the structure of any public GitHub repository visible in minutes, and points at the code paths most likely to be exploitable.

The problem

Developers lose a lot of time on unfamiliar code: which function calls which, what is dead, and where user input ends up. Security reviewers have the same question in a sharper form: can untrusted input reach a dangerous call?

What I built

  • Parsing: Tree-sitter parsers for Python, JavaScript, TypeScript, Java and Go extract modules, classes, functions, imports and calls into a graph stored in PostgreSQL.
  • Code graph: an interactive D3 force-directed graph (drag, zoom, click to inspect) plus Mermaid architecture diagrams.
  • Ask AI: code chunks are embedded with sentence-transformers into pgvector, so questions like "where is authentication handled?" are answered with retrieval-augmented generation (RAG) grounded in the actual source.
  • Dead code: functions and classes with zero incoming calls or imports, ranked by confidence, with entry points skipped.
  • Security: taint analysis that walks the call graph (breadth-first, up to 6 hops) from user-input sources to dangerous sinks: eval/exec, shell=True, SQL built with string formatting, and pickle. Each finding gets an on-demand LLM explanation of why it is exploitable and how to fix it.

Honest limitation: the analysis works at the call-graph level, so a tainted value may not actually reach the sink at runtime. The UI says so, and labels each finding with a confidence level.

What I learned

Static analysis is a precision game. Most of the work went into resolving calls correctly (self.method, Class.method, module functions) because every wrong edge becomes a false positive in the security view.
