Pharma Prescriber Analytics Copilot

A sales-operations team wants to know which prescribers are growing, how demand for a drug will move next year, and to ask ad-hoc questions without writing SQL. This project answers all three on real public data.

The data

Real CMS Medicare Part D prescriber data, at the grain each task needs: state-level demand series from 2013 to 2024 for forecasting, and prescriber-level detail from 2022 to 2024 for segmentation. Scope: 4 drugs (Metformin, Atorvastatin, Amoxicillin, Anastrozole) across 4 states (CA, TX, NY, FL).

69.7Mclaims
518,946provider-drug-year rows
187,436prescribers
12 yrsof demand history

What I built

  • Pipeline: ingest → clean → EDA → segmentation → forecasting, rerunnable with one command and checked by GitHub Actions CI on every push.
  • Segmentation: K-Means clusters prescribers by behaviour; a classifier predicts each prescriber's likely next-period growth.
  • Forecasting: Prophet vs XGBoost vs LSTM compared with walk-forward cross-validation, so models are judged on years they never saw.
  • Serving: a FastAPI service (/segments/{npi}, /forecast/{drug}/{region}, /ask) and a Streamlit dashboard.
  • Text-to-SQL assistant: an agent that writes SQL, runs it read-only, and answers from the actual rows, so every number is auditable.
  • Monitoring: a retrain job flags drift when forecast error (MAPE) exceeds 1.5× its historical average.

A design decision worth defending

Why text-to-SQL and not RAG? The questions this data invites ("which specialty prescribes the most X in CA", "how did claims change year over year") are aggregations: a GROUP BY, not a document search. Generating SQL and answering from real rows avoids made-up numbers.

What I learned

data.cms.gov blocks non-US traffic, so the pipeline supports a rotating US proxy for real downloads and a clearly labelled synthetic fixture for CI. Being explicit about which numbers are real mattered more than any model choice.
